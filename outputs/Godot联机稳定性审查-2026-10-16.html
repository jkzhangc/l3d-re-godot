L3D RE / NETWORK REVIEW

互联网延迟抖动与回弹：
存在确定的优化空间，不能只继续调 Ping 和插值延迟

本轮确认了独立于公网质量的预测碰撞差异，以及可复现的插值、共享有序流和四人快照超 MTU 问题。TCP 隧道仍可能放大这些问题。

审查时间：2026-10-16 · 代码基线：2d0bfb2f · 验证引擎：Godot 4.6.3 · 未修改游戏业务代码、配置或公网服务
结论旧修复主要发现验证结果建议顺序真机验收边界与文件

一、先说结论

延迟数字跳动、自己的角色被拉回、别人或敌人来回抖动，是三个不同的问题。目前实现里三者都有可解释的风险链，不能把它们统一归因于“网不好”，也不能以 HUD 数字更平稳作为网络已修好的依据。

32 / 32现有中继及房间目录测试通过；证明功能可用，不代表弱网平稳。
4 类实证预测碰撞不一致、插值边界、跨 RPC 有序淘汰、四人包超 MTU。
0 业务改动只增加隔离探针和报告；原游戏脚本、config.json、服务端源码未改。
优先建议：先修“客户端和主机算出来不一样”与“旧/异常数据被当新数据”这两类确定问题，再瘦身快照、补测量；最后用同场景对照数据判断是否升级 UDP 数据面。不要先全量重写，也不要仅放宽回弹阈值。

二、之前的修复到底覆盖了什么

已有修改评价没有解决的部分
TCP 两端关闭 Nagle正确，能减少小包合并等待。TCP 丢包重传、有序交付、队头阻塞依然存在。
1d82e74a：纠偏 RTT 估计快涨慢降可减少死区因单次 Ping 骤降而反复误纠。没有输入编号、ACK、回放；不能修复碰撞不一致、旧快照和长断流。
c8ba7ff7：HUD 改 EMA改善数字可读性，保留原始 RTT 给预测侧。仅改变显示，并没有让网络数据更快或更均匀到达。
敌人插值下限 15 → 21ms，上限 60ms平稳 60Hz 条件下比 15ms 合理。外推仍开启；突发批量交付、丢包、渲染时间回退仍可抖动。
敌人每包最多 12 条限制了敌人分片体积。玩家 29 字段包未瘦身；不同分片仍共用一个 ordered 流。

因此，之前并非“完全没修好”，而是修了部分表现和局部触发点，但互联网稳定性的底层链路仍未闭环。本轮不把未经实机复测的历史修复当作已验收。

三、当前互联网链路

TCP 某段丢失时，后续游戏数据要等待恢复；表现常是“停一下，然后一批数据同时到”。房主 Tunnel 在 _process 转发，低 FPS 或主线程卡顿也会使交付成批；二者会相互叠加。put_data 在发送缓冲紧张时可阻塞，服务端 socket.write 也没有背压处理与队列指标。

证据：script/tunnel_client.gd:168–215、244–256、338–359；master-server/src/tunnel_relay.js:132–156、327–338。TCP 队头阻塞是结构事实；用户本次抖动中所占比例未做公网抓包确认。

四、主要发现：按处理优先级

P11. 自己的回弹：客户端可穿过敌人，主机却会被敌人挡住

源码确认 + 物理最小复现玩家碰撞 mask 为 11，包含敌人层 8。主机敌人保留 body；但客户端敌人进入纯表现模式时，_disable_network_simulation() 把 CollisionShape2D 关闭。两端虽调用相同移动函数，物理世界并不相同。

隔离场景用生产的层、mask 和矩形尺寸：玩家从 x=0 向 x=150 移动，敌人中心 x=100。主机停在 x≈77.93，客户端走到 x=150，位置差 72.07px。即使网络零丢包，这个差异也足以触发拉回；继续走会扩大差距。

建议：明确“玩家是否应被敌人实体挡住”的预测规则。如果保留阻挡，客户端要有与权威时间关系清楚的简化碰撞代理，而不是直接启用滞后渲染敌人的全部 AI/判定；如果改变两端阻挡规则，会影响玩法，不能擅改。优先测试贴怪、尸潮挤墙和转角。

证据：object/player.tscn:20–23；object/enemy.tscn:21–30；script/enemy.gd:1017–1029；script/network_world.gd:1345–1373、1402–1446；script/player.gd:371–374。最小测试只验证碰撞差异，不是完整战斗回放。

P12. 敌人外推：同毫秒到达会把 4px 差值放大为约 680px 额外位移

生产插值源码隔离复现外推速度使用“位置差 ÷ 本地到达时间差”，分母最小仅 0.0001s；只限制外推时长 17ms，没有限制速度或位移。同毫秒处理两条不同位置快照时，4px / 0.0001s = 40,000px/s，外推得到 x≈684，而最新样本仅 x=4。

复现使用生产插值脚本的内存副本，只替换时间函数为可控时钟，未改公式。玩家远端默认不开外推，对照结果停在 x=4；敌人生产入口确实传入 true。

建议：使用 Host tick/快照时间差估算速度；合并或拒绝零/异常时间差；加实体合理速度及位移上限；传送、死亡和形态突变清历史。不要仅把21ms再调大。

证据：script/network_snapshot_interp.gd:96–120、134–144、160–161；script/enemy.gd:488–491、539。680px 是构造边界实测，不代表已在用户真机观测到同幅跳跃。

P13. 玩家包与敌人分片共用 ordered 序列，会互相淘汰

真实本地 ENet 乱序复现player_position_snapshot 和 player_snapshot 都用默认通道的 unreliable_ordered。先发玩家包，再发敌人包；人为让敌人包先到、玩家包后到，接收结果只有 [enemy]，玩家更新被淘汰。

这是按网络流排序，而非按 RPC 名或敌人分片排序。一个后发的小分片先到，会让较早、包含其他实体的大分片失去价值，增加有效快照间隔。

建议：玩家与敌人独立流；多敌人分片采用明确的实体/分片新鲜度语义。可用无序不可靠传输 + 每实体 tick 拒旧，或稳定分片对应独立序列。不能只改成 unreliable 而不做新旧判定。仅分离玩家/敌人也不足以解决敌人各片互淘汰。

证据：script/network_world.gd:530–556、3267–3279、4856–4872。注意默认通道0对 reliable/unreliable_ordered/unreliable 分别独立；本问题是两个 ordered RPC 共流，不是可靠流在 ENet 内直接挡住不可靠流。下层单TCP又是另一层阻塞。

P14. 四人玩家状态包已能超过 MTU；高频负载仍夹带低频数据

代表性真实 RPC 实测当前每人29字段，每秒60轮，包含昵称、角色路径、装备ID、弹匣字典、备弹字典等。采用真实字段顺序和代表性短昵称/手枪状态，在隔离 Godot 的实际 RPC 中测得：

玩家数Variant 数组字节本地捕获 Host→Client UDP 载荷结果
1392B406B收到
2776B790B收到
31160B1174B收到
41544B拆成多个数据报，另有控制包收到，但触发超MTU警告
WARNING: Sending 1548 bytes unreliably which is above the MTU (1392),
this will result in higher packet loss

准确解释：超过MTU不等于本机必然丢弃，本次四人测试也收到了一次RPC；问题是额外分片和弱网下更高的丢失风险。上述为生产格式的合成状态，不是实机整局抓包，不同昵称/库存会改变长度。

建议：位置、朝向、移动、必要动作状态留在高频热路径；昵称/角色/装备结构改为可靠变更事件或低频状态，保留版本与完整恢复通道；按实际 RPC 编码字节预算做门禁，不能只数条目。

证据：script/network_world.gd:119–122、4953–5019。敌人单条Variant实测84B，12条数组1016B，[空玩家数组,敌人数组]参数容器1032B；这些容器值仍不等于最终UDP线上包长。

P15. 可靠旧全量包可能覆盖更近的位置和状态

源码确定缺少防护；完整重传时序待测可靠全量世界快照约每2秒发送；高频位置包同时到达。包里没有 Host tick、快照序号、生成时间或场景 epoch。若可靠全量包重传迟到，它仍被当成最新状态完整应用，旧坐标会进入预测校正或远端插值。

插值器只认接收时刻，隔离输入“100 → 104 → 迟到旧坐标80”最终会渲染80，证明该层没有拒旧能力。但本轮未对生产 world_snapshot 做真实丢包重传端到端复现，故不把这个时序冒充实测根因。

建议：统一快照生成 tick 与场景 epoch，按实体/状态域拒绝旧动态状态。可靠结构同步可以补实体，但不能无条件覆盖较新的位置、HP、装备域。大包 resync 与战斗事件分可靠通道，避免应用层排队；注意 TCP 下层仍共享。

证据：script/network_world.gd:3229–3248、3328–3341、3436–3463、3632–3669、3678–3694。远端玩家一次可靠重同步还可能分别经 apply_network_resync_state 和 apply_network_presentation 重复推入同坐标样本（player.gd:745、653）。

P1 / P26. 预测仍是 RTT 死区启发式，不是输入确认与重演

源码确认输入包只有方向和慢走标志，Host 保存最后一份输入持续模拟，没有输入编号、确认号、时间戳和超时归零。客户端也没有重演尚未被主机确认的输入。停步包迟到时，Host 会继续按上次方向走；反向、短断流和碰撞差异后，只能靠距离纠偏兜底。

当前偏差超过 96px 先硬吸附，再考虑 RTT 死区。以默认250px/s匀速简化估算，约0.4秒的位置滞后已接近/越过阈值；它不受“Ping平滑”保证。这里是模型推演，不是网络真实临界值。

建议：先补输入有效期、生成tick与接收记录；正式 reconciliation 需围绕固定模拟tick定义输入持续时间/编号、Host确认点、客户端回放未确认输入，并明确动态碰撞与击退处理。不能只加一个seq字段就宣称完成预测回滚。后续把物理校正和视觉平滑分开，避免在渲染帧直接写碰撞体位置引出穿墙/解重叠抖动。

证据：script/network_world.gd:1331–1446、3040–3056；script/player.gd:472–493、667–711。

P27. 自适应渲染时间会倒退，且 Ping 不足以诊断卡在哪层

渲染时刻直接取 now - render_delay()。缓冲突然增加10ms，而实际只过5ms时，播放时刻会倒退。本轮批量样本测试中，单向前进轨迹渲染值从17.375降到16.144，回退约1.23px。应改为单调播放游标，通过短时放慢/加快追赶目标缓冲，而不是倒放历史。

当前可靠 Ping 每秒一次，测到的是公网往返 + 可靠队列/重传 + 游戏线程调度 + 隧道搬运；HUD EMA只是数字滤波。它没有样本过期提示、P95/P99、快照年龄、有效丢失率、缓冲耗尽次数、硬纠偏次数、TCP排队和主机帧耗时。

证据：script/network_snapshot_interp.gd:109–144；script/network_manager.gd:728–822。远端玩家22–55ms、敌人21–60ms仅为收到样本后的附加缓冲范围，绝不是互联网端到端延迟上限。

五、还有哪些流量与 CPU 优化空间

  • 每2秒可靠全量重同步仍按客户端重复构建：高频路径已做到只构一次，但 _broadcast_reliable_world_snapshot 在每个peer循环内调用三种构造函数；可先构一次只读快照，再编码/发给各端。
  • 热路径临时分配较多：玩家每轮先建字典再转数组，包含字典复制；敌人也先构完整字段再转紧凑数组。手机Host下应测构建耗时和内存分配，再简化。
  • 60Hz全量敌人状态随活敌数线性增长：按实测84B/条粗算，50只×60Hz=252,000B/s/客户端，仅条目；三个客户端共756,000B/s，还没算玩家、头部、可靠事件及重传。这是模型下限，不是本局线上流量。
  • 考虑变更驱动/距离分级而非无条件降频：先压缩低频字段和未变化状态；再对远处、非交互实体评估低频，近身敌人与本机输入优先。变更同步需有可靠基线/恢复逻辑，不能让一次丢包永久缺字段。
  • 不要在透明ENet隧道中随意丢“看起来旧的UDP包”：一个数据报可能混有可靠事件、ACK和不同通道内容。要丢旧位置，应在应用层可分类处处理；隧道层背压至少要有可观测的上限、失败策略和partial-write顺序。

七、建议实施顺序

阶段建议工作验收目标与注意事项
A · 先止住确定错误外推零时间差/异常速度保护；单调插值游标；梳理敌人预测碰撞；修测试退出码。加本轮反例为回归。碰撞方案要保留玩法，不盲开所有客户端敌人判定。
B · 数据新鲜度与负载tick/epoch及域版本；玩家/敌人流分开；分片按实体拒旧；热/冷字段分离，包长门禁。四人最坏昵称/库存不再触发MTU警告；旧包不覆盖新位置；乱序不让其他实体更新白丢。
C · 预测与可观测性输入超时、固定tick命令、ACK/重演；纠偏记录；RTT分位数、更新间隔、包龄、FPS、隧道队列。停止/反向/贴怪/断流恢复可复测；不靠放宽96px阈值掩盖。
D · 传输升级先测背压和主线程转发；TCP作为兼容回退，探索房主主动建映射的UDP数据面，控制仍可TCP。维持ENet与Host权威模型；处理认证、NAT映射续期、地址漂移及手机网络；不是直接暴露房主公网端口。

取舍：完全保留TCP隧道可以减少重构，但不能承诺消除丢包下队头阻塞；UDP数据面更符合实时位置更新“新包比旧包重要”的语义，但需要服务端与客户端配套修改。先拿A–C结果，再决定D投入更稳妥。

八、真机复测怎么做才有结论

建议先用相同地图、相同人数/敌人量，对照“局域网直连”和“互联网自动中继”；切换电脑Host与手机Host，至少测2人和4人。先定义可接受阈值，下面项目不得只看平均Ping：

动作/环境主要定位应记录
空地长跑→急停→反向输入时序、陈旧坐标、死区与硬吸附。实际校正像素、硬拉次数、最新确认输入、样本年龄。
贴怪、穿尸潮、背后靠墙两端动态碰撞是否一致。同一输入下权威与预测轨迹、碰撞对象。
看队友和敌人匀速移动插值/外推、乱序与成批交付。每实体更新间隔P95/P99、同帧样本数、耗尽/外推次数。
射击密集、掉落物多、每2秒附近可靠全量突发和队列阻塞。可靠队列、包长、Host构建耗时、帧耗时尖峰。
可控0/1/3/5%丢包、短暂200–500ms停流重传、恢复与输入有效期。不把旧快照当新快照；断流后无长期旧方向行走。
切图、倒地、复活、受击/击退epoch、重置与特殊状态一致。旧场景包拒绝、生命/碰撞恢复、合法瞬移单独标记。

若空地也回弹，优先查输入/快照时间；若贴怪才明显，优先查碰撞差异；若整屋同时停再冲，优先查TCP/房主线程；若只在四人或敌人多时明显，优先查包长、带宽和构建尖峰。这些是定位线索，不代替日志证据。
